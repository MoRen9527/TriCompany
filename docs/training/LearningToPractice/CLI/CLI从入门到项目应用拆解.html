CLI 从入门到项目应用拆解

这份 HTML 的目标，不只是承载一篇教程，而是成为一个可继续长成“3WSchool 式教学页 + 项目练习壳”的单页入口：中间负责讲概念，右侧负责让学生立刻试，底部或侧边负责展示输出与反馈。

内容层 概念解释、最小例子、常见误区、项目案例。
交互层 选择题、补全题、代码输入框、提示、答案与进度。
执行层 本地 JS、后端沙箱、项目代码运行与受控工作区。

1. 这个文件应该先承担什么角色

第一版最稳的目标，不是直接做全功能在线 IDE，而是先把“教程产品的骨架”搭出来。也就是说，这个文件先承担四件事：稳定布局、课程结构、练习插槽和输出区域。等这些固定之后，再去接 Python、Node、Go 或项目代码运行。

为什么不能只有正文

如果只是长文档，学生会看完一个概念再忘一个概念。教程页要把“看懂”立即变成“动手”，这样才能把 CLI 从知识变成肌肉记忆。

讲解区 示例区 练习区 输出区

第一版必须留出的接口

  • 题目容器：选择题、填空题、代码题。
  • 运行入口：本地运行或后端运行按钮。
  • 输出面板：stdout、stderr、状态提示。
  • 提示与答案：渐进式揭示，而不是直接把答案贴在正文里。

2. 每个教学单元的节奏

建议每个 lesson block 都遵循同一节奏：概念 - 最小例子 - 立即练习 - 运行反馈 - 常见错误 - 延伸到项目。这样课程既不会散，也便于后面把内容抽成 JSON/manifest 驱动。

  1. 先给学生一个可抓住的概念定义。
  2. 马上给一个能复制的最小示例。
  3. 接着安排一次简短练习，让学生马上动手。
  4. 给出结果反馈、提示和解析。
  5. 最后把这个概念拉回真实项目里的使用场景。

3. 示例：讲完概念，立刻让学生动手

下面这个示例故意做得很小：先讲“CLI 的最小单位是什么”，再安排一个判断题和一个命令输入练习。真正的教程页应当由很多这样的 block 组成。

概念

CLI 的最小学习对象

CLI 不是“记很多命令”，而是理解命令、参数、输入、输出、工作目录五件事如何联动。只要学生能读懂一条命令是“谁在做什么，用了哪些参数，对哪个目标生效”，他就开始具备项目应用能力了。

python hello.py --name TriCompany

# 拆解
# python      -> 解释器 / 命令
# hello.py    -> 要运行的目标文件
# --name      -> 命名参数
# TriCompany  -> 参数值
项目应用

为什么这里要立刻练

因为 CLI 学习最容易出现“看懂例子，但不会自己写命令”。所以讲完定义后，必须马上给一道能动手的题，不论它是选择题、命令补全题，还是实际运行题。

  • 入门阶段：先做选择、排序、补全。
  • 中级阶段：开始改示例代码并运行。
  • 项目阶段：直接对真实仓库脚本或代码做小改动，再运行验证。

4. 程序运行层该怎么接

这个 HTML 现在可以负责内容层和交互层，但真正要跑 Python、Node、Go 或仓库里的现成代码，仍然要把执行层设计清楚。最稳的拆法如下：

浏览器内可直接运行

  • HTML / CSS / JavaScript 示例。
  • 简单校验题与前端交互练习。
  • 本地字符串解析、命令结构理解练习。

必须走后端沙箱

  • Python / Go / Rust / Shell / Node 真运行。
  • 对现成代码库的脚本、测试、命令执行。
  • 项目级练习的受控修改、重置与输出隔离。

也就是说，这个文件的正确姿势不是“把所有执行都塞进前端”，而是前端负责教学编排，后端负责安全执行。

5. 后续为什么建议用数据驱动

当课程一多，你不应该继续手写一堆散落的 HTML 结构。更稳的做法是让 lesson、exercise、solution、runnerType 都写在 manifest 里，再让页面按 JSON 生成教学区和练习区。这样以后扩 Python、项目练习、进度记录都更容易。

{
  "exerciseId": "cli-run-001",
  "type": "code-run",
  "language": "python",
  "runnerType": "backend-sandbox",
  "starterCode": "print('Hello, CLI')",
  "checkMode": "stdout",
  "expectedOutput": "Hello, CLI"
}
