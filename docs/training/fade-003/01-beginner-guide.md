# FADE-003 小白版——公司的学习笔记是怎么记的

## 文档同步元信息

- syncMode: source-only
- lastSyncedAt: 2026-09-09

读者：完全零基础的新人。不需要懂 FADE 协议。
目标：30 分钟后，你能说出"一条经验从想记到记完"要过哪几关，并读懂一条真实审计记录。

---

## 一、一句话说清这是什么

> 公司有一本周记（每周一册），谁在工作中踩了坑、悟了招，就往当周那册里记一条。
> **FADE-003 把"记一条"做成了带质检的流水线：先领号、再过审、排版上版、打分、主编签字——
> 全程一个编号（runId）贯穿，每一步都留痕。**

它的分数是全公司实例里最高的（98/100），但它的出身是一个**真实翻车**：2026-08-18 之前，
有个 agent 记周记时跳过规范、自创结构、还把内部 commit 索引表塞了进去——公司据此立册，
把"记周记"从靠自觉变成了靠流水线。

## 二、为什么需要它（立册前的三个真实翻车）

规范正身里原样记着三条反模式，每条都是真事：

1. **跳过规范查找**：没读固定格式，凭记忆开写——自创了"理论小节"结构。
2. **跨周找旧模板**：格式该以最近一周为准，实际抓了 4 周前的旧模板，错过了格式演进。
3. **内部台账入册**：把 commit 哈希索引表塞进周记——那是工程审计信息，不是能对外分享的共学内容。

教训的本质：**写什么靠判断（人的活），格式、位置、去重、脱敏必须靠规则（机器的活）**。
FADE-003 就是把后半句做成了 CLI。

## 三、只需要先懂三个词

**1. runId（一条周记的身份证）**
动笔之前先"领号"（`begin` 命令），拿到一个 8 位编号。之后过审、上版、打分、签字，每一步
都报这个号——审计日志里凭它能拼出这条周记完整的一生。

**2. 五件结构（固定格式）**
每条周记固定五件：**现象 / 具体表现 / 解决方案 / 问题影响 / 当前经验（项目经验+模型自查）**。
格式由 CLI 代码保证（JSON 进、固定结构出），不依赖 agent 自觉——这就是"确定性"。

**3. 收口五查（C1-C5）**
写完不算完：落盘路径对不对（当周目录）／五件齐不齐／文件头更新没／git 提交没／回报 CEO 没。
五查全过才给签字（APPROVED）。

## 四、一个比喻贯穿全程：给公司周刊投稿

- **begin（领号）** = 到编辑部登记领稿号，顺便查重（同题提示）
- **qualify（过审）** = 初审两件事：格式齐不齐＋**脱敏扫描**（API key、私人内容一律拦下）
- **append（上版）** = 排版进当周那册，自动编为 2.1、2.2……只追加不改旧文
- **score（打分）** = 机检部分（S1-S7：结构/元信息/去重/链路/脱敏复扫/守恒）+ 评委打分
  （W1-W4：现象捕捉/方案可操作/影响真实/经验提炼）
- **close（签字付印）** = 主编终审。**注意：主编的签字机器还要再验一遍**——机器验不过，
  你签"approved"也没用，先给你退回（ESCALATED）。这是这家周刊最硬的一条规矩。

## 五、活体证据：审计日志里的三条真实一生

打开 `TriMetaverse/docs/workflow/operating-records/项目级 AI 共学周记/journal-run-log.jsonl`，
每行一个 JSON，按时间排——这是流水线的监控录像：

**第一生（脱敏拦下真钥匙）**：
```json
{"runId":"0f1a4035","action":"qualify","verdict":"ESCALATED","hits":["疑似 API key（sk-…）"]}
```
有人差点把 API key 写进周记——脱敏扫描当场拦下，转人工裁决。**这一行就是"机器守门"的实证。**

**第二生（先碰壁再走通）**：
```
541da30c begin → QUALIFIED → append BLOCKED（当周文件不存在）→ init 建草稿 → QUALIFIED → APPENDED（2.1）
```
一个真实 run 的完整弯路：文件不存在被挡→先建草稿→重走→成功。BLOCKED 不是失败，是流水线
在告诉你"缺一步前置"。

**第三生（98 分登顶）**：
```
7a85e3e0 begin → QUALIFIED → APPENDED(2.2) → score PASS（机检满分 80+评委 18/20=98）→ APPROVED
```
全公司实例最高分的诞生记录——2026-08-28，FADE-003 凭这条 run 升格完整档。

**第四生（机器否决主编）**：
```
541da30c close ESCALATED（agent 签的是 approved！）→ close APPROVED
```
同一稿第一次 close，agent 判"过"，机器查 run 链不过——**先 ESCALATED**；补齐后第二次
close 才 APPROVED。"Close CLI 是校验者而非发起者"不是口号，是日志里的一行。

## 六、最小体验：读懂一条审计链（纯读，零风险）

1. 打开上面的 jsonl，任选一个 runId，把它的所有行按时间拼起来。
2. 对照第四节的生命周期，说出这条 run 走到了哪一步、卡在哪（如果有）。
3. 打开 W35 周记（`docs/workflow/operating-records/2026-W35/project-ai-community-weekly-2026-W35.md`），
   找到 2.1 和 2.2 两条——它们就是第二生和第三生的成品。

**验证**：能指着日志说出"这条 run 的哪一步被谁拦过、最后怎么过的"——小白版毕业。

## 七、三个最常见的新人疑问

**Q1：什么该记、什么不该记？**
四问：**可复述**（有具体现象）？**有产出**（有方案或教训）？**可对外**（脱敏后能分享）？
**有共学价值**（对"用 AI 做项目的人"通用）？四问全过才记；内部工程台账（commit 索引、排期）
不入册——那是第三条翻车的教训。

**Q2：写错了能改吗？**
能，但有铁律：**只追加不改旧文**是默认；修订走 RETRY 通道——评分不过线退回重做
（stage=score），修订后**必须重评**（retry 之后同 runId 有 score PASS 才允许 APPROVED，
机器可校验）。别人已签发的条目是绝对禁区。

**Q3：最近几周怎么没见新周记？**
如实现状：现存周记在 W34/W35，W36/W37 尚无新册——记周记的触发目前还是手动/指令
（自动化挂 backlog），有值得记的才记，不是每周硬凑。这属于实例的诚实边界，不是故障。

## 八、带走的三句话心智模型

1. **先领号再动笔，一个号走到底**——审计链的根。
2. **格式机器管，判断人来管**——五件结构/去重/脱敏是 CLI 的事，四问/语义裁决是 agent 的事。
3. **机器可以否决 agent 的"approved"**——校验者不发起，发起者不终裁。
