# FADE-006 小白版——计划写完，谁来开工？

## 文档同步元信息

- syncMode: source-only
- lastSyncedAt: 2026-09-07

读者：完全零基础的新人。不需要懂 FADE 协议。
目标：30 分钟后，你能说出"一份计划从写完到自动开工"的完整旅程，并看懂一棵真树。

---

## 一、一句话说清这是什么

> FADE-006 是公司的**自动开工流水线**：把写好的计划（任务说明书+任务树）挂到每周工作台
> 的"待拾取"架子上，满足条件的，服务器上的"吊车"（自动侦测）会自动抓走、派给合适的
> 员工执行、盯到做完、收好回执——**全程不需要任何人催**。

它的前身问题只有一句话：**计划写完还要人推着做**——写计划的人得记得安排执行、
盯着进度、催办、收尾。人一忙，计划就躺在文件夹里过期。

## 二、为什么需要它（手工推计划的三个坑）

1. **忘推**：计划写好了，安排执行的事一忙就忘，三天后想起来黄花菜凉了。
2. **漏盯**：执行到一半出故障，没人发现，任务静默烂尾。
3. **说不清**：做完之后"当时照哪份计划做的、材料有没有被改过"——没有凭证。

FADE-006 的解法是把"推"这件事整个交给机器：**落盘即入队，双通道自动拾取，自治执行到收口，
材料全程防篡改**。2026-08-26/27 的首场实战（P0 审计修复战役）就是它一口气自治跑完八个任务。

## 三、只需要先懂三个词

**1. 任务树（tree）**
一份计划的执行拆解图，登记在每周工作台的 `trees/<树名>/tree-op.json` 文件里。树上有若干
**节点**（node），每个节点是一件具体的活，指派给某个员工角色。树文件就是这套流水线的
"包裹面单"。

**2. 三重门（拾取条件）**
吊车不是见单就抓——面单要过三道检查，全过才拿：

| 门 | 白话 | 不过会怎样 |
| --- | --- | --- |
| `status=active` | 计划**定稿了**，不是草稿、不是待批 | 吊车不拿，单子躺在架上 |
| `server-executable` | 这活**能在服务器上干**（别是只能在某人电脑上干的活） | 不拿，避免抓起来干不了 |
| `pending` 无时间门 | 待干的活**没带"等某个时间再说"的条件** | 带时间门的活等条件满足的下轮 |

另有一个分拣维度：**face 路由**——面单上写了这活归哪条执行线（本地线还是服务器线），
送错线的活不算数。

**3. 卷封（sealing）**
计划引用的原材料（哪些文件、哪些锚点）在开工前**封存指纹**（hash）。执行时第一件事是
"验卷"：材料跟封存时一模一样才准开工；不一样就停下报告——**防的是"计划照着 A 写，
执行时 A 被人改成了 B"**。

## 四、一个比喻贯穿全程：快递分拣线

- **计划文档** = 商家的发货方案
- **tree-op.json** = 每个包裹的面单（收件人=执行角色、内件清单=节点、封条=卷封）
- **挂平面**（push 到 sg-bare） = 包裹上传送带
- **双通道拾取** = 扫码机：传送带末端的**高速扫码**（git hook，push 后秒级触发）为主，
  每 30 分钟一班**巡回扫码车**（cron :18/:48）兜底——高速口漏扫的，巡回车补
- **三重门** = 扫码机的三个感应器（定稿？能在本仓干？没挂时间牌？）
- **编排层** = 分拣调度员：按面单把包裹分给对应工位的机器人（spawn 执行会话），一次一件
- **节点报告** = 每件包裹的签收回单（干到哪一步、装了什么、门禁过没过）
- **Merkle root 存档** = 整批交接单的防伪总章：一批活干完，把所有回单算一个总指纹入档，
  之后任何人想改任何一张回单，总章对不上

## 五、活体证据：现在就有一棵"没被拿走"的树

打开本周工作台：`TriMetaverse/docs/workflow/operating-records/2026-W37/trees/duty-night-patrol/tree-op.json`

你会看到 `"status": "pending"`——**这就是它还躺在架子上没被拾取的原因**（三重门第一关：
active 才拿）。这棵树的 source 字段写着它出自哪道令、acceptance 写着验收标准、nodes 列着
三个待办节点。等它定稿改 active、推上远端，流水线自动接手。

对照组：`2026-W35/trees/` 里有九棵**已经干完**的树（P0 战役+教程树），它们的 status 与
节点全是收口态——pending 与 done 两态对照看一遍，这套流水线就"活"了。

彩蛋：W35 那批 `fade-tutorial-001..007-deep` 树，正是当年**用 FADE-006 流水线生成
FADE 系列教程**的树——这套流水线连你正在读的教程前辈都是它做的。

## 六、最小体验：读一棵树（不碰生产）

流水线的吊车在服务器上，本机不跑它；新人第一课是**读懂面单**：

1. 打开上面 W37 的 tree-op.json，找出五个字段：`treeId`（单号）、`status`（当前状态）、
   `face`（归哪条线）、`acceptance`（怎么算干完）、`nodes`（几件活、派给谁）。
2. 对着三重门说一遍它现在为什么没被动。
3. 再去 W35 随便开一棵收口树，对比 status 和 nodes 的状态差异。

**验证**：能指着字段说出"它为什么还没被拾取、干了之后回单会记什么"——小白版毕业。

## 七、三个最常见的新人疑问

**Q1：自动拾取会不会乱干活？**
不会，四层保险：①三重门挡住未定稿/不可执行/带时间条件的树；②**人批准才 active**——
status 从 pending 改 active 本身就是人的决定；③卷封制保证照原计划干，材料被动过就停；
④预算双门（每日 token 台账+月度金额）挡住跑飞。机器只放大"已批准的计划"，不产生新决定。

**Q2：执行一半出故障怎么办？**
流水线自带"分层取证"：工具被拒、通道缺失、push 失败……每类故障有预置的定位方法和解法锚
（三天实战总结的"六面墙"速查表，见产品版）。规则是：出事先取证定层，不自作聪明重试到好。

**Q3：它和我听过的周平面迁移（FADE-001）、发布管线（FADE-002）什么关系？**
三个实例各管一段：FADE-001 管**工作台翻页和日志兜底**（每周日/每 10 分钟），FADE-002 管
**真源到发布面的同步**（改了真源谁去铺副本），FADE-006 管**计划到执行的自动派工**
（批准的计划谁去干）。它们共用同一套 FADE 协议（十段、卷封、评分、终态门）——学完一个，
另外两个的骨架你已经懂了。

## 八、带走的三句话心智模型

1. **挂单即入队，过门才派工**——定稿（active）是人的决定，抓取是机器的事。
2. **验卷开工，回单收工**——材料对不上封条不开工；干完每件活留结构化回单。
3. **高速口＋巡回车**——双通道拾取，秒级响应，兜底不漏。
