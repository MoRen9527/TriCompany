## 二 · 指纹定义（`content_sha256_16`·三处实现须逐字同此）

**算什么**：对**整份 charter 文件的文本**算（JSON 形与 `.md`/YAML 形同一算法）。

**规范化 C(file)**——四步·顺序不得变：

1. **解码**：按严格 UTF-8 解码。**U+FEFF（BOM）作为普通字符计入·不剥**。解码失败（非 UTF-8）→ **按原始字节**算 sha256（不做下面 2、3 步）。
2. **置空两键的值**（文本层·**禁 parse→dump 重序列化**——跨语言 dump 必不一致）：把 `content_sha256_16` 与 `commit` 两键的**字符串值**替换为空串·**引号保留**·不重排、不动其他任何字节。
   - **JSON 形**：从首个 `"cao_approval"` 出现的位置起、至文末，逐行查找带引号的键 `"content_sha256_16"` / `"commit"`·每键只处理**首次出现**。
   - **YAML/`.md` 形**：**只在首个 `cao_approval:` 块内**（自该行起、到缩进回退到该行缩进层级或遇 `---` 止）查找裸键 `content_sha256_16` / `commit`·每键首次出现。
   - **值内转义**：值的闭引号=首个**未被反斜杠转义**的 `"`。
   - **为何两键都置空**：指纹字段本身在文件里——对「已填指纹的文件」算指纹，值随自身变、永不相等；`commit` 是信息字段、入库后回填，不置空则回填即破签。
   - **为何限定起点/块内**（实测抓出·见 §五）：全文找键名会命中**排在块之前的字符串值里形如 `content_sha256_16: "…"` 的文字**——占掉「首次出现」·真键反而不被置空·签后改那段文字门看不见。
3. **换行归一**：**只把 `\r\n` 替换为 `\n`**；**孤立的 `\r` 不动**（与 git autocrlf 行为一致）。
4. **哈希**：对结果的 UTF-8 字节算 sha256·取**前 16 位小写 hex**。

**批准方与门用同一函数**（同一份参考实现·不得各自实现两套）。

**计数字段 `n`**（仅用于校验·不进指纹）：规范化时命中的键数。正常件 **n=2**；非 UTF-8 走原字节分支 **n=-1**。门校验 **n 必须为 2**（缺键即 schema 不全=拒）。

## 三 · 拒因码（四值·拒因可分·每条附 detail/expected/fix）

| code | 触发 | 修复动作 |
|---|---|---|
| **`CAO_NOT_APPROVED`** | G1：缺 `cao_approval` 块 / `approved !== true` | 先经 CAO 批 |
| **`FINGERPRINT_MISSING`** | G2：`content_sha256_16` 缺或空 | CAO 签时算指纹并填入 |
| **`CONTENT_CHANGED`** | G3：字段值 ≠ 当前文件指纹 | 内容已变·须 CAO 重签 |
| **`GATE_TOOL_FAIL`** | G0：读/解码/解析/计算失败·或 n≠2 | 修文件编码/语法/schema·或修工具 |

**铁律**：
- **「取值失败≠空值」**——任何工具/解析失败一律 `GATE_TOOL_FAIL`·**不得当作字段为空而落放行**（v1.0 骨架实测：`jq` 缺失时取值全空→落宽容面→**放行一切**·含假锚与内容不符）。
- **无宽容面**：v1.0 的「commit 空／指纹无值／文件不可读→放行+note」四条**全部退役**。「弱绑定」通道不再存在——**没有指纹就是不能挂**。
- 已退役的 code：`ANCHOR_MISMATCH`／`ANCHOR_UNVERIFIABLE`（锚验退役·不再产生）。

## 五 · 效力边界（如实·不虚标）

1. **指纹无密钥**——防的是**过失**（改了内容忘重签·换机器重检出·编辑器动换行），**不防越权**：能改文件的人重算指纹再填入即可通过。**防越权需文件外锚**（受保护的批准台账/sidecar·CAO 域所有·他席不可写——或签名）。此为后续件·**另立需求候 CEO**·本规范不声称具备。
2. **在 charter 门上走不到的两条**（被更早的拒因覆盖·如实列出免得实现方疑惑）：
   - **非 UTF-8 的 charter**：任务书是 JSON/UTF-8 文本·非 UTF-8 必先撞解析 → `GATE_TOOL_FAIL`。「原字节分支」在指纹函数里存在·但 charter 门上到不了。
   - **带 BOM 的 charter**：**待 CTO 裁**（见 §六-1）——现状是「指纹可设计成通过·但门在解析步先拒」·两条裁定叠加后自相矛盾。
3. **「全过」≠「好任务书」**——只等于「形合格·CAO 批过且批后内容未变」。

## 六 · 待裁一项（入册时如实留白·裁后补）

**1. BOM 的处置**——CTO 22:45 裁「U+FEFF 计入指纹·三语言行为一致」。但 CAO 跨语言对表实测（Python 与 JS 两套独立实现·10 组向量）：**JS/TS 的 `TextDecoder` 默认剥 BOM、Python `bytes.decode('utf-8')` 默认保留**——同一带 BOM 件两语言指纹不同（JS 加 `{ignoreBOM:true}` 后 10/10 一致·**指纹层已可对齐**）。剩下的是指纹层与解析层的叠加：

| 路线 | 做法 | 实测后果 |
|---|---|---|
| **A**（③ 原裁） | BOM 计入指纹 + 门严格解码后直接解析 | 带 BOM 件**永远过不了解析**（U+FEFF 在串首）→「BOM 计入」在 charter 门上**走不到** |
| **B** | 门**仅解析层**先剥 BOM·指纹仍对含 BOM 的原字节算 | 自洽：带 BOM 件能过；**签后加/删 BOM 仍被检出**（指纹层管） |
| **C** | BOM 两侧都剥·不计入 | 签后加/删 BOM **门不管** |

CAO 倾向 **B**（保住 ③ 的本意「BOM 变动可检出」·又不让带 BOM 的件卡在解析）。**候 CTO 定·定后本节改写为条文。**
