## 二 · 指纹定义（`content_sha256_16`·三处实现须逐字同此）

**算什么**：对**整份 charter 文件的文本**算（JSON 形与 `.md`/YAML 形同一算法）。

**规范化 C(file)**——四步·顺序不得变：

1. **解码**：按严格 UTF-8 解码。**U+FEFF（BOM）作为普通字符计入·不剥**（指纹层口径——**门在解析取字段时另剥·见 §六**·两件事勿混）。解码失败（非 UTF-8）→ **按原始字节**算 sha256（不做下面 2、3 步）。
2. **置空两键的值**（文本层·**禁 parse→dump 重序列化**——跨语言 dump 必不一致）：把 `content_sha256_16` 与 `commit` 两键的**字符串值**替换为空串·**引号保留**·不重排、不动其他任何字节。
   - **JSON 形**：从首个 `"cao_approval"` 出现的位置起、至文末，逐行查找带引号的键 `"content_sha256_16"` / `"commit"`·每键只处理**首次出现**。
   - **YAML/`.md` 形**：**只在首个 `cao_approval:` 块内**（自该行起、到缩进回退到该行缩进层级或遇 `---` 止）查找裸键 `content_sha256_16` / `commit`·每键首次出现。
   - **值内转义**：值的闭引号=首个**未被反斜杠转义**的 `"`。
   - **为何两键都置空**：指纹字段本身在文件里——对「已填指纹的文件」算指纹，值随自身变、永不相等；`commit` 是信息字段、入库后回填，不置空则回填即破签。
   - **为何限定起点/块内**（实测抓出·见 §五）：全文找键名会命中**排在块之前的字符串值里形如 `content_sha256_16: "…"` 的文字**——占掉「首次出现」·真键反而不被置空·签后改那段文字门看不见。
3. **换行归一**：**只把 `\r\n` 替换为 `\n`**；**孤立的 `\r` 不动**（与 git autocrlf 行为一致）。
4. **哈希**：对结果的 UTF-8 字节算 sha256·取**前 16 位小写 hex**。

**批准方与门用同一函数**（同一份参考实现·不得各自实现两套）。

**计数字段 `n`**（仅用于校验·不进指纹）：规范化时命中的键数。两键都在=2；**只有指纹键=1（`commit` 键可缺——它是信息字段·不参与判定·签时没有也能挂**·2026-11-27 23:11 裁）；非 UTF-8 走原字节分支 **n=-1**。门校验 **n ≥ 1**（n<1=两键在文本里都定位不到=门无从对表指纹=`GATE_TOOL_FAIL`）。**不再要求 n=2。**

   **关于 `commit` 键**：置空的只是它的**值**·键名本身仍是指纹定义域的一部分——所以「签时没有该键」能挂、「签后把整个键删掉」会被检出（`CONTENT_CHANGED`·文件确实变了）、「签后给该键回填值」不影响（三种情形均实测·见回归 R-b/R-b2/R-b3）。

## 三 · 拒因码（四值·拒因可分·每条附 detail/expected/fix）

| code | 触发 | 修复动作 |
|---|---|---|
| **`CAO_NOT_APPROVED`** | G1：缺 `cao_approval` 块 / `approved !== true` | 先经 CAO 批 |
| **`FINGERPRINT_MISSING`** | G2：`content_sha256_16` **缺／空／畸形**（长度≠16·含非小写-hex 字符）——均为内容层问题 | CAO 签时算指纹并填入（畸形=重签·不是修工具） |
| **`CONTENT_CHANGED`** | G3：字段值 ≠ 当前文件指纹 | 内容已变·须 CAO 重签 |
| **`GATE_TOOL_FAIL`** | G0：门**无法评估**——读/解码/解析/计算失败·或两键在文本中都定位不到（n<1） | 查编码/语法·或修工具。**内容问题不归此码** |

**铁律**：
- **「取值失败≠空值」**——任何工具/解析失败一律 `GATE_TOOL_FAIL`·**不得当作字段为空而落放行**（v1.0 骨架实测：`jq` 缺失时取值全空→落宽容面→**放行一切**·含假锚与内容不符）。
- **无宽容面**：v1.0 的「commit 空／指纹无值／文件不可读→放行+note」四条**全部退役**。「弱绑定」通道不再存在——**没有指纹就是不能挂**。
- 已退役的 code：`ANCHOR_MISMATCH`／`ANCHOR_UNVERIFIABLE`（锚验退役·不再产生）。

## 五 · 效力边界（如实·不虚标）

1. **指纹无密钥**——防的是**过失**（改了内容忘重签·换机器重检出·编辑器动换行），**不防越权**：能改文件的人重算指纹再填入即可通过。**防越权需文件外锚**（受保护的批准台账/sidecar·CAO 域所有·他席不可写——或签名）。此为后续件·**另立需求候 CEO**·本规范不声称具备。
2. **在 charter 门上走不到的两条**（被更早的拒因覆盖·如实列出免得实现方疑惑）：
   - **非 UTF-8 的 charter**：任务书是 JSON/UTF-8 文本·非 UTF-8 必先撞解析 → `GATE_TOOL_FAIL`。「原字节分支」在指纹函数里存在·但 charter 门上到不了。
   - ~~带 BOM 的 charter~~：**已闭合**——见 §六（裁定 B：解析层剥 BOM·指纹层计入·带 BOM 件可正常挂载且 BOM 变动可检出）。
3. **「全过」≠「好任务书」**——只等于「形合格·CAO 批过且批后内容未变」。

## 六 · BOM（U+FEFF）处置——裁定 B（CTO 2026-11-27 22:59 裁·CAO 入条文）

**指纹层与解析层分开·各走各的**：
- **指纹层**：U+FEFF **计入**——按严格 UTF-8 解码·BOM 作为普通字符保留（§二第 1 步不变）。
- **解析层**：门在**把文件当 JSON/YAML 解析取字段时**、**仅此一步**先剥去串首的 U+FEFF。
- **判读层不变**：G0–G3、C1–C6 的顺序与拒因码都不受 BOM 影响。

**为何这样裁**（实测依据）：
- 若两层都「计入」（原裁·路线 A）：带 BOM 的 charter **指纹能对上·却永远过不了 JSON 解析**（U+FEFF 在串首）——「BOM 计入」在 charter 门上走不到。CAO 跨语言对表实测·CTO 复核。
- 若两层都「剥」（路线 C）：签后加/删 BOM **门不管**——丢了「BOM 变动可检出」。
- **B**：带 BOM 件能正常挂载；签后加 BOM、删 BOM **均被检出**（`CONTENT_CHANGED`）。两全。

| 情形（实测 8/8） | 结果 |
|---|---|
| 无 BOM 件·正常签 | PASS |
| 带 BOM 件·指纹对含 BOM 的原字节算 | PASS |
| 签后**加** BOM（原无） | `CONTENT_CHANGED` |
| 签后**删** BOM（原有） | `CONTENT_CHANGED` |
| 带 BOM·未批 | `CAO_NOT_APPROVED`（解析后准入先判） |
| 带 BOM·内容改 | `CONTENT_CHANGED` |
| 同一带 BOM 件按路线 A | 卡在解析 `GATE_TOOL_FAIL`（证明 B 必要） |

**实现须知的两个语言坑**：
1. **JS/TS `TextDecoder` 默认剥 BOM、Python `bytes.decode('utf-8')` 默认保留**——指纹层在 JS/TS 须显式 `{ignoreBOM: true}`（名字反直觉：true=不剥）·或用 `Buffer→utf8`。跨语言向量 **V04** 即此案。
2. 解析层的「剥」**只许用于取字段**·**不得**把剥过 BOM 的文本再拿去算指纹。
